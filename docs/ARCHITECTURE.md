# Cloud Visual Academy: architecture

## Overview

```
curriculum/            ← single source of truth (JSON, versioned with the code)
  <exam>/objectives.json   official outline, generated by scripts/sync_exam_objectives.py
  <exam>/sync-report.json  added / retired / renumbered objectives from the last sync
  <exam>/lessons/*.json    lessons (16-section format, one lesson may cover several objectives)
  <exam>/questions.json    original questions, each tied to one objective id
  animations.json          registry of interactive animations, fidelity label and test file
  az-104/sprint-plan.json  14-day sprint: day → official skill ids
  coverage-report.json     generated by scripts/validate_coverage.py

frontend/ (React + TS strict + Vite + Tailwind 4 + Motion + React Flow + Recharts)
  src/simulations/   pure, deterministic models (nsg, rbac, replication, subnet), unit-tested
  src/animations/    SVG primitives + interactive simulations built on the models
  src/services/      curriculum loader, API client, sprint planner, exam engine
  src/pages/         dashboard, course, lesson player, sprint, diagnostic, practice, …

backend/ (FastAPI + SQLAlchemy 2 + SQLite + Pydantic 2)
  learner history only: lesson progress, attempts, exam sessions, review schedule,
  bookmarks, settings. No curriculum content lives in the database.
```

The frontend imports curriculum JSON at build time, so content is always available. The backend
stores only learner history. When the backend is offline the UI still works, says so in the header,
and shows no history rather than invented numbers.

## Objective identity

IDs are positional (`AZ104-4.2.1` = domain 4, skill 2, objective 1) and stable across syncs:
the sync script fingerprints the normalised objective text and keeps the existing id when the text
is unchanged, even if it moved. New text gets a new id. Objectives that disappear are kept with
`status: "retired"` and listed in `sync-report.json`. CLF-C02 objectives are each "Knowledge of"
and "Skills in" bullet under a task statement, so `CLFC02-3.5.4` is the 4th bullet of task 3.5.

## Coverage vs mastery

* **Content coverage** (validator, per objective): complete lesson (all required sections), registered
  animation whose test file exists, ≥ 2 questions including ≥ 1 applied type, a lab when the
  objective is hands-on, and an official documentation link. Human verification is reported separately
  and never counts towards coverage.
* **Learner mastery** (backend): % correct over the last 6 attempts, shown only after ≥ 3 attempts.
  An objective is *weak* below 70 %, or after a repeated mistake or a confident wrong answer.

`scripts/validate_coverage.py` exits 1 while any objective is incomplete and 2 on integrity
errors (unknown objective ids, invalid answers, non-official doc links).

## Spaced repetition

Completing a lesson schedules its objectives the same day. Correct reviews move them through
+1, +3 and +7 days, then weekly. A wrong answer resets the objective to the next day. Every scheduled
objective is due again the day before the exam date set in Settings.

## Sprint planner

`services/sprint.ts` is a pure function. Each objective has a budget (30 min hands-on, 18 min
conceptual), × 1.6 when weak, 5 min when already completed and not weak. Each day gets its fixed
activities plus the daily recall check. Work that does not fit rolls to the next day; anything still
left at day 14 is reported as overflow, and the plan is flagged unrealistic. Nothing is hidden.

## Animation engine

* `useStepper`: play/pause, next/previous, restart, speed. Steps are data, so the same timeline drives
  the SVG, the accessible text transcript and tests.
* `AnimationControls` + keyboard shortcuts (←/→, space, R) when the animation has focus.
* `primitives.tsx`: original SVG shapes for users, VMs, servers, firewalls, public IPs, disks, scopes
  and packets. No vendor icon files are used.
* Motion is turned off when the OS has `prefers-reduced-motion` set.
* Each simulation emits lab validation ids (`onLabCheck`) when the learner reaches a required state.

## Fidelity labels

`accurate-model` means the logic implements documented rules (NSG priority processing and order,
RBAC union, inheritance and NotActions, Azure subnet maths). `simplified-illustration` means the
layout follows the documentation but timing or scale is illustrative (storage geo-lag).
